# Fork changelog

Changes made in the ehd-themis fork on top of upstream Open WebUI. Upstream's release notes stay in
[CHANGELOG.md](CHANGELOG.md), which each upstream sync replaces; fork entries live here so they don't conflict with it.

## [Unreleased]

### Added

- 🔐 **The database can be encrypted at rest, and backups can be encrypted.** `DATABASE_TYPE=sqlite+sqlcipher` now starts the application (upstream's request engine refused such URLs, so it could not run), with the password from `DATABASE_PASSWORD_FILE` or `DATABASE_PASSWORD`. `utils/sqlcipher_tool.py` converts an existing `webui.db` both ways with verification and keeps the original, and `scripts/hermes-backup.sh` writes age-encrypted, rotated backups for a public key. Adds the dependency `sqlcipher3-wheels`. Off by default; uploads, the vector store and logs are not covered. See [docs/ENCRYPTION.fork.md](docs/ENCRYPTION.fork.md).
- 🧩 **One API request can use the caller's own tools AND server tools (MCP), and a plain HTTP request now runs its `tool_ids`.** Upstream ignores `tool_ids` as soon as the body carries `tools`, and it runs the tool loop only when the request has a chat id and a message id (event emitter, answer over the websocket, chat saved): a plain `POST /api/chat/completions` with `tool_ids` such as `server:mcp:m365` connected the MCP server but never ran its tools and handed the model's `m365_…` calls back to a caller that could not run them. Now (native function calling, `stream: true`, nothing saved, no websocket): **(1)** `tools` + `tool_ids` are both offered to the model; the caller's specs come first and a name used by both belongs to the caller (logged). **(2)** A turn whose tool calls are all server tools is run here, with the person's own OAuth token, and the next turn streams on in the same response. **(3)** A turn with at least one caller tool call runs its server calls first, then the response ends with `finish_reason: "tool_calls"` carrying only the caller's calls (renumbered from 0). **(4)** A request with a chat id and message id (chat UI, Teams bridge) keeps the upstream loop; only a request that mixes `tools` and `tool_ids` takes the new one whatever its ids. No change when only `tools` is sent. Server tools only run for `tool_ids` the person may use (same access check as before); built-in, terminal and direct tools stay out of plain HTTP. All of it lives in `backend/open_webui/utils/api_tool_loop.py`; the hooks in `utils/middleware.py` (the `mixed_tools` block in `process_chat_payload`, `wants_api_tool_loop` in `streaming_chat_response_handler`, connection errors recorded) and `main.py` (MCP clients are closed by the stream, not before it is read) are a few lines each. Extra information rides in the non-standard top-level chunk key `open_webui`, which OpenAI clients ignore:
  - `{"open_webui": {"tool_connection_errors": [{"server": "m365", "error": "auth_required" | "unavailable" | "failed"}]}}`, the first event of the stream when a requested connector could not be used (the person has not connected it yet, no access, server down). Today's behaviour stays: the request goes on without that connector.
  - `{"open_webui": {"server_tool_call": {"id", "name", "status": "completed" | "failed"}}}`, one per server call as soon as it has run (progress for the caller; no arguments, no result).
  - On the final chunk (`finish_reason: "tool_calls"`) when server calls were made in this response: `{"open_webui": {"server_tool_calls": [{"id", "type": "function", "function": {"name", "arguments"}, "status", "result"}]}}`, every server call of the response in order, with its result (text, binary data replaced by a marker, cut to `CHAT_RESPONSE_TOOL_RESULT_MAX_CHARS`). To continue, the caller appends ONE assistant message whose `tool_calls` are these calls followed by its own, then a `tool` message per server call (the `result`) and one per caller call (its own result), and sends the history back as usual.
  - Text and reasoning deltas are relayed as they arrive; the usage of the last turn is sent in a usage chunk. At the tool-call limit (`CHAT_RESPONSE_MAX_TOOL_CALL_ITERATIONS`) the last turn is asked without tools. Not covered: `stream: false` (server tools do not run there, as upstream) and legacy function calling.
  - Tests: `backend/open_webui/test/test_api_tool_loop.py` (only caller tools, only server tools, mixed turn, caller call after a server turn, failing tool, missing authorisation, provider error, round limit, MCP clients closed).
- 🔑 **Several API keys per user, each rotated or deleted on its own.** Settings > Account lists a user's keys with a name, creation date, last use and optional expiry (none, 30 days, 90 days, 1 year); a key is created with a name, and the secret is shown once, on creation or rotation. Rotating or deleting one key leaves the others working, so revoking one integration (Word add-in, Teams bridge, a script) no longer forces every other integration to be updated. Administrators see the same list in the user dialog, can rotate or delete one key, or delete all of a user's keys. A key past its expiry stops authenticating, and `last_used_at` is recorded at most once a minute. New endpoints under `/api/v1/api_keys` (own keys, and `/users/{user_id}` for administrators); keys are managed with a session only, so an API key cannot create, rotate or delete keys. Existing keys keep working and show up as "Default key". The legacy `/auths/api_key` and `/users/{id}/api_key` endpoints are unchanged (they still replace or delete every key of the user). No schema change: the `api_key` table already had the columns. Up to 20 keys per user.
- 🔁 **A long tool run ends with an answer, and a looping one is stopped early.** When a reply reaches the tool-call limit (`CHAT_RESPONSE_MAX_TOOL_CALL_ITERATIONS`), the last completion is sent without tools and with a note asking the model to summarise what it found and say what is left, instead of the chat ending on a "limit reached" error; the user can reply "continue" to carry on. A new `CHAT_RESPONSE_TOOL_CALL_REPEAT_LIMIT` (default 3, 0 to turn off) adds a warning to the result when the same tool is called with the same arguments that many iterations in a row, and takes the tools away two repeats later.
- ✂️ **A tool result can no longer fill the model's context window.** A file a tool downloads as base64 (a 224 KB PNG from the Microsoft 365 `download-bytes` tool came to about 245k tokens and overflowed a 262k window) is replaced with a marker such as `[binary PNG data, 224 KB, not shown]`, and any other result is cut to `CHAT_RESPONSE_TOOL_RESULT_MAX_CHARS` characters (default 30000, 0 turns the cut off) with a note saying how much was left out. The cut applies when messages are built from the stored output, so a chat that already holds an oversized result works again; the full text stays visible in the chat.
- 🚦 **The model selector shows whether the AI is ready before a message is sent.** A dot beside each model (and on the selector button) reads the `lachesis` field the gateway puts on its `/v1/models` entries, which Open WebUI already passes through under `model.openai`: ready (with the estimated stop time), starting (minutes left), asleep (the first message starts it), stopped or unavailable. The list refreshes every 15 s while the chosen model is starting. Models without the field, or from other connections, show nothing.
- 🧭 **Responses-only clients such as Codex can use Hermes.** `POST /api/responses` (also `/api/v1/responses`) accepts the OpenAI Responses API, converts it to Chat Completions, runs it through the regular chat pipeline (presets, model access, connection headers) and answers in Responses format, as a JSON object or as a stream of `response.*` events. It works with chat-only gateways and is stateless: the full conversation goes in `input` and `previous_response_id` is refused with a 400. Function tools and Codex's freeform tools (e.g. `apply_patch`) are supported, reasoning is returned as a summary, and the built-in tools with no chat equivalent (`web_search`, `local_shell`, ...) are ignored.

### Changed

- ⬆️ **Synced to upstream v0.13.5.** Upstream now stops a tool that fails twice with the same arguments and asks for a final answer at the iteration limit; the fork keeps its own notices (the iteration limit and repeated identical calls that succeed) in place of upstream's generic prompt. Upstream's `TOOL_OUTPUT_MAX_CHARS` (unset by default) is applied after the fork removes base64 blobs; the fork cap `CHAT_RESPONSE_TOOL_RESULT_MAX_CHARS` still applies when model messages are built.
- 🏷️ **IDE autocomplete is forwarded as a task.** `/api/completions` requests that carry no `metadata.task` are now marked `task: "autocomplete"`, so a connection header templated with `{{TASK}}` (e.g. `X-Gateway-Task`) arrives as `autocomplete` instead of empty and gateways can tell autocomplete from interactive chat. The chat-completions fallback for providers without a native `/completions` route is marked the same way. A task set by the caller is kept.
